# FieldLinker Display 新Webクライアント開発方針

## 目的
- 既存の `webclient/` を置き換える次世代 UI を実装し、WebSocket 経由で LED フレーム送信・確認をより快適に行えるようにする。
- Raspberry Pi 実機・シミュレーター双方を同じ UI で操作できることを前提に、今後の機能拡張を見越した構成にする。
- 新要件: 2 つの螺旋ディスプレイ（LED パネル）を同時に制御できる UI を提供し、それぞれのフレームを並列に送信・管理できるようにする。

## 技術スタック
- **フロントエンド**: 純粋な HTML + CSS + バニラ JavaScript（ES Modules）
- **ビルド工程**: なし（必要なら `npm` のみで lint/format を追加）
- **描画**: 既存と同じく Canvas API (2D)
- **依存ライブラリ**: 極力ゼロ。必要になった場合のみ軽量なユーティリティを個別導入

## 機能要件（初期スコープ）
1. WebSocket 設定・接続管理（ディスプレイごとに接続先 URL/IP を分けつつ、共通UIで制御）
2. フレーム生成ツール（単色、ランダム、パターン、ブラシペイント）
3. LED プレビュー（`pixel_map.json` を読み込み、Canvas で編集＆閲覧）
4. ログビュー（送信/受信メッセージ、エラーを表示）
5. 自動送信・フレーム保存/読み込み（将来的に）

## アーキテクチャ指針
- `src/` を UI/ロジック/描画ユーティリティで分離し、テストしやすい構造にする。
- WebSocket クライアントをクラス化し、接続管理と再接続ロジックを集中。
- `pixel_map.json` は Fetch + キャッシュで扱い、2 パネルとも同じ配置データを参照（後続で API 取得に切り替え可能）。
- ディスプレイごとに WebSocket 接続インスタンスを持ち、個別の IP/ポート設定を保持できるようにする。
- Canvas レンダラは「フレームバッファ（Uint8Array）」を入力に描画する純粋関数として構成し、ブラシ操作も同モジュールで完結。

## 今後の進め方
1. HTML/CSS/JS のベースファイル雛形を作成（ディスプレイ A/B 用のセクションを用意）
2. 基本 UI レイアウトとスタイル（接続/編集/ログ/プレビューをディスプレイごとに配置＋共通操作欄）
3. WebSocket ラッパーとログ表示（複数接続を管理できるよう構造化）
4. フレームバッファ管理（2 面分のバッファ、生成関数、ブラシ編集）
5. Canvas プレビューと `pixel_map.json` ローダー（各ディスプレイに紐づけ）
6. 自動送信制御・設定保存（ディスプレイごとの間隔・オン/オフ）
7. テスト・ドキュメント整備

## メモ
- 基本は `python -m http.server` や `npm serve` などで静的配信し、追加ビルドは不要な構成とする。
- 既存 `webclient/` と共存させるため、ビルド成果物は `webclient_v2/dist` 以下に出力し、`python -m http.server dist` 等で配信できる形を想定。
